# 自适应 V2 协议

## 目标

V2 用于新的统一 `qrtransfer-cli` 两端，默认支持任意文件。它在屏幕二维码数据通道之外，继续使用键盘按键作为反向确认通道，但将原版“每次轮询都翻页”改成可靠的停等确认：当前页没有正确接收前，发送端不会提交文件偏移。

V2 的目标是检测传输意外错误并自动恢复，不提供加密、身份认证或对抗恶意篡改的能力。

## 二维码帧

所有多字节整数使用大端序。帧尾的 CRC32C 覆盖其前面的全部字段。

文件头包含：

- 魔数 `QRT2`、协议版本和帧类型；
- 随机会话 ID，用于拒绝其他传输残留在屏幕上的二维码；
- 文本标志；
- 文件总字节数；
- 16 字节 MD5；
- CRC32C。

数据页包含：

- 魔数、协议版本、帧类型和末页标志；
- 会话 ID；
- 页号；
- 文件起始偏移；
- 载荷长度与原始载荷；
- CRC32C。

独立测速使用专门的测速头，包含会话 ID、二维码尺寸以及最小、初始和最大页面大小。测速头不会被正式文件接收流程识别为文件头；其后仍使用相同的数据页和 CRC32C，但载荷为发送端生成的合成数据，接收端只统计而不写入文件。

ZXing 的公共二维码写入接口以文本为输入。Safe/Balanced 以及旧 V2 使用带 `QRT2:` 前缀的 URL-safe、无填充 Base64，确保 ZIP 等任意字节序列稳定往返。Fast 使用带 `QRT2R:` 前缀的 ISO-8859-1 单字节映射，将每个帧字节直接映射为一个二维码字节，取消 Base64 约 33% 的体积膨胀。接收端自动识别两种前缀；帧校验、会话、偏移和自适应控制不受编码层变化影响。

Fast 默认以 768px 二维码承载 2700B 页面，并在连续成功后升至 2800B；发送端仍会先做本机二分容量校准，无法本机往返的容量不会用于实际发送。紧凑编码要求两端使用支持 `QRT2R:` 的新版统一 CLI；新版接收端继续兼容旧 V2 Base64 页面。

## 确认与重传

页号奇偶用于让重复按键幂等：

| 按键 | V2 含义 |
|---|---|
| `1` | 确认偶数页；文件头阶段请求第 0 页 |
| `2` | 确认奇数页 |
| `3` | 否定确认偶数页，请求降低密度并重传 |
| `4` | 否定确认奇数页，请求降低密度并重传 |
| `0` | 发送端重置到文件头 |
| `5` | 仅用于测速，由接收端通知测速发送窗口停止并输出统计 |

接收端只有在会话、页号、偏移、长度和 CRC32C 全部正确后才写入载荷并确认。二维码未刷新、暂时不可见或仍是上一页时只继续截图，不重复发送“下一页”。重复页只重新确认相同奇偶页，不重复写文件。

发送端在收到否定确认时保留当前文件偏移，降低页面大小并重新生成同一页，因此恢复不会跳过字节。最终输出还必须同时通过文件大小和 MD5 校验。

## 自适应参数

启动时，发送端在 `--min-page-size` 与 `--max-page-size` 之间二分测试当前 `--qr-size` 下本机可往返识别的最大页面，然后从 `--initial-page-size` 开始：

- 连续成功 4 页：增加 128 字节，不超过校准后上限；
- Safe 收到否定确认后全局页面大小乘以 0.7，不低于下限；
- Balanced/Fast 收到否定确认后只将当前页乘以 0.7，该页成功后下一页恢复目标大小；
- 临时降密页不参与连续成功升速计数；
- `--fixed-page-size`：关闭页面载荷升降，但仍保留逐页确认和校验。

Safe 接收端记录从确认到识别出新页面的耗时，并使用 EWMA 调整下一次首次截图等待：

```text
EWMA = 0.8 × 旧值 + 0.2 × 本次耗时
下一等待 = clamp(0.75 × EWMA, minDelay, maxDelay)
```

Balanced/Fast 默认主动等待为 `0ms`，截图、解码、按键确认和远程桌面刷新本身构成实际页面周期。一次 `--frame-timeout` 仅记录并继续扫描；同一预期页连续达到 `--downshift-after-timeouts` 次完整超时后才发送否定确认，默认阈值为 `3`。重复页会重新确认并清零连续超时，但不会触发降密。

Safe 默认每次完整超时就发送否定确认，并将等待时间乘以 1.5，最大不超过 `--max-delay`。用户显式传入延时参数时仍使用相同 EWMA 公式，但延时不会改变连续超时降密阈值。

实际吞吐近似为：

```text
有效吞吐 = 每页有效载荷 ÷（远程刷新 + 截图识别 + 确认按键周期）
```

增大二维码像素可以改善高密度二维码的模块清晰度，但不会突破 QR 版本容量。Balanced/Fast 的零主动等待并不代表页面周期为零；它只是不再在远程桌面实际刷新耗时之外附加固定等待。Fast 相比 Base64/Legacy 的主要吞吐优势来自更高的单页有效载荷，而不是取消 CRC、页序或最终 MD5。

## Legacy 模式

`send --legacy` 生成原版文件头和 Protobuf 页面，使用 `1/2` 翻页，可供原版接收端读取。`receive --legacy` 使用原版二维码解析、固定 `--page-delay` 和 MD5 校验，可读取原版发送端。

V2 和 legacy 不自动混用。新双端默认 V2；与任意原版端配对时必须在新端显式传入 `--legacy`。

## 测速模式

`benchmark-send` 使用和 Fast 正式发送相同的本机容量校准、当前页临时降密及按键确认，但持续生成确定性的合成二进制载荷。`benchmark-receive` 默认零主动等待、连续三次完整超时后才请求当前页降密，在指定时长到达后发送停止按键，不创建临时文件，也不执行文件 MD5。

接收端以全部成功页计算持续平均速度，以 10 秒滑动窗口计算峰值，并使用最后 60 秒成功样本的保守分位数估算稳定页面大小、页面周期及推荐参数。测速只反映当次屏幕分辨率、缩放、网络和远程刷新环境，不会自动覆盖内置 profile。
